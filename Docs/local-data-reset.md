# Local data reset · #71

19 October 2026. Independent HomeView prototype feature; no Apple owner pairing, Siri state reset or original F101 parity claim. [Introduction and services](setup-and-services.md).

## User flow and scope

Settings → Reset local data shows the scope before any deletion. Fresh public LocalAuthentication device-owner authentication and a separate exact `RESET` confirmation are required. Authentication expires after 60 seconds and is cleared on backgrounding, locking, profile changes or dismissal. Demo profiles do not authenticate a reset, and reset authentication does not unlock connected personal services. Cancellation, denial, expired authentication and write failures do not report success. Read-only/newer stores are refused.

The reset clears this app's local Snapshot, imported photo copies, recovery files, synthetic content, dialogue/drafts, service consent and preferences. It stops this app's audio, media and asynchronous writers before they can refill cleared state. It returns to a pending introduction with no connections. Source calendars, reminders, Photos, Music libraries and accounts are not deleted; OS grants are not revoked. A non-content identifier for an already-created reminders source list is retained to avoid creating duplicates. Home remains disconnected.

Registered native alarm/timer identifiers and in-flight scheduling block reset. Where the public AlarmKit API applies, denied or unverifiable existing app-alarm state also blocks it; reset does not silently forget or cancel OS alarms. Unsupported authentication/platform paths do not manufacture success; the reduced Watch app does not expose this reset UI.

## Storage failure and recovery

A fresh private state directory is prepared before a same-parent Darwin atomic directory exchange. Captured directory descriptors and device/inode identity checks constrain cleanup to the old app-owned directory, without following symlinks. Preparation/write/sync/exchange failures leave the old logical state intact. Observed path retargeting prevents subsequent persistence through the changed path.

If old-file cleanup cannot finish, the fresh logical state is committed but the app explicitly reports incomplete cleanup and retains a non-content cleanup journal. **Retry old reset file cleanup** requires fresh authentication and targets only that journaled old directory; it does not reset new content. A second full reset cannot overwrite an outstanding cleanup record. This is logical local cleanup, not secure SSD erasure, an arbitrary-filesystem sanitizer, or a cross-process/power-cut guarantee.
