# Assistant context boundary · #34

19 October 2026. This is acceptance of the **current bounded data-access policy**, not implementation of personal Siri context or system-wide onscreen awareness. F042/F045 remain blocked and original parity false. Apple Home remains disconnected.

## Data and purpose inventory

| Source/state | Existing public or own route | Assistant text-model use |
| --- | --- | --- |
| Explicitly submitted text, including text the user pastes | Send; at most four temporary exchanges | The only content sent to the concrete on-device provider. There is no automatic submission or implicit enrichment. |
| Calendar/reminders | EventKit through own connected views; separate saved source choice, OS permission and device authentication | Not connected. Source permission and device unlock are not consent for Assistant sharing. No context-sharing switch or adapter is enabled. |
| Photos/albums | Public Photos access and own display-selection consent | Not connected; no images, captions, identifiers or catalogue enter the text provider. |
| Music/weather | Existing explicitly connected service UI, bundled media or city weather | Not connected; no tracks, playback state, city results or credentials enter the text provider. |
| Mock home, timers, recipe and own page/selection | Explicit local command controls and fixed parser; route/scene/overlay state also authorizes interaction | Not appended to AI prompts. Local commands are a separate mode; no AI answer is parsed as an action. |
| Own demo profiles/messages | Synthetic local UI records; a profile is not device authentication | Not read by the Assistant. Selecting a profile cannot grant source/model rights. |
| Siri conversation, Apple Messages history, another app or system screen | No corresponding adapter/tool in this build | Not available. No screenshot/OCR, screen enumeration, Siri-context takeover or cross-app retrieval is added. This is an observation of this build, not a universal claim that every future public Apple integration is impossible. |

Existing native service controllers and the existing tool-free typed-text provider already provide these separations; no context framework, plugin, account integration or paid service is introduced. User-supplied text can of course contain information the user chooses to paste: this policy prevents **implicit source reads**, not the user's explicit text submission or a model inventing an answer.

## Enforced boundary

The callable AppModel entry checks the active scene flag, Assistant route and absence of call/doorbell coverage before running commands or sending text. Enabling the provider also requires that context. These checks are in the model, not just disabled buttons. Actual route change synchronously discards AI conversation and pending plans before a SwiftUI callback is needed. Unrun plan text is restored only as an unsent draft; ordinary unsent drafts still survive navigation.

Inactivity revokes pending AI conversation except while the existing explicit readout device-authentication flow owns the system prompt. That narrow inactive exception keeps the selected answer for a **later explicit Read tap**; it never grants Send authority or automatically starts speech. Actual background/lock still invokes the existing lock path, clears conversation/drafts and invalidates sessions. No physical LocalAuthentication or App Switcher snapshot behavior is claimed by the synthetic sequence.

The provider receives a String prompt and maintains only its temporary conversation. Its production construction remains concrete SystemLanguageModel, tools empty, no cloud fallback and no app-data instructions. Device authentication, OS permission and source purpose remain distinct: connected views may request permission without enumerating locked records; lock/session generation prevents stale reads/permissions from restoring access. Assistant purpose is unconditionally off for these sources, including when their own views are unlocked. A future personal-context feature would require its own authenticated purpose-scoped design and acceptance; this delivery does not preauthorize it.
